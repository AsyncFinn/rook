# Content

`rook-content`: references, providers, the cache and the decoders. Part of the [architecture](../architecture.md).

- **References** are parsed once, into `ContentRef` (`rook-content/src/reference.rs`): `rbxasset://<path>` (a client file), an asset id with an optional version (`rbxassetid://`, and the legacy `http://www.roblox.com/asset/?id=` URLs in all the shapes Studio accepts), an asset version id, and `rbxthumb://` (parsed, not resolved). Anything else, including the empty string, is no content rather than an error. The accepted shapes follow Studio, checked form by form ([asset fetching](../../behavior/content/asset-fetching.md)). Files store content in the `Content`-typed properties (`MeshContent`, `TextureContent`, `AudioContent`); the legacy string properties scripts use (`MeshId`, `Texture`, `SoundId`) are views of them in `rook-lua`, and consumers read the `Content` ones (`Value::content_url`).
- **Providers**, tried in the `contentOrder` setting's order (default `overrides,defaults,install,folders,delivery`; [settings](../data-and-logging.md#settings)):
  1. *Overrides* (`overrides.rs`): the user's own files for asset ids, from the data folder's `overrides` folder ([data and logging](../data-and-logging.md#overrides)). The folder is read once per resolver, so a reference costs a table lookup, and a file wins over the cache, including a refusal the cache remembers.
  2. *Rook defaults* (`defaults.rs`): a table of the 2009 client's `rbxasset://` paths that now stand for public assets (`fonts/sword.mesh` → 12221720). Rook's head mesh is generated in `rook-render`, not shipped here.
  3. *The Roblox install*: the newest Studio or player version folder under `%LOCALAPPDATA%\Roblox\Versions` (and `Program Files`, and the macOS app bundles), or `ROOK_ROBLOX_INSTALL`; `rbxasset://` paths are looked up in its `content`, `ExtraContent` and `PlatformContent/pc` folders, ignoring case.
  4. *Material textures* are a `ContentRef::Material` no string names: `materials.rs` gives the TexturePack asset Studio uses for each material and set, and the pack and the images it names resolve through asset delivery and the cache like any asset, arriving decoded.
  5. *Content folders* (`ROOK_CONTENT_DIRS`): downloaded content packages or local overrides, laid out like `content`.
  6. *Asset delivery* (`delivery.rs`) for asset ids, through the cache: anonymous `assetdelivery.roblox.com/v2/assetId/<id>` requests, then, for assets refused anonymously, the Open Cloud endpoint with the user's key if one is saved, read only then ([the Open Cloud key](../data-and-logging.md#the-open-cloud-key)). Nothing else is ever sent anywhere, and no browser cookie or credential is read. The `assetDelivery` setting controls the network; left out, the player and `rook content` default to on, headless runs and tests to off.
- **Kept content** (`kept.rs`): the materials' and terrain's texture packs and their images, pinned to asset versions and kept for good in the data folder's `content\assets` rather than the cache ([data and logging](../data-and-logging.md#kept-content)).
- **Cache** (`cache.rs`), the data folder's `cache` folder: content-addressed blobs (BLAKE3) plus one small file per reference giving its blob, or the failure. Rook keeps it under the `cacheMaxSize` setting (2 GB) itself: reading a blob marks it used (its modified time, at most hourly), and each resolver opening the cache trims the least recently used blobs, and the references they leave, on a background thread. `rook cache` shows, prunes by age or clears it. A cache where older Rooks kept it (`%TEMP%\Rook\cache`) is moved in once, file by file when both exist, leaving behind anything that fails to move for the next try. Files are written to a temporary name and renamed; blobs are checked against their size and hash when read and refetched if damaged. "Not found" and "forbidden" answers are kept for a day, so a place with hundreds of dead ids asks the network once a day at most; network errors are only remembered for the run. A second run needs no network.
- **Off the engine thread**: a `Loader` (one per DataModel, made on the first request) runs resolutions on four worker threads and shares one resolution between duplicate requests. The DataModel takes scripts' new requests and delivers finished ones once per frame, just before `wait()` resumption, so `PreloadAsync` callbacks run and calls return on the engine thread. A place that never asks for content starts no threads and pays nothing per frame. No async runtime: plain threads and channels.
- **Decoders** live with the content: `mesh.rs` reads Roblox mesh files (versions 1.00 to 7.00, Draco-compressed 7.00 included) and union geometry and collision hulls itself into one vertex and index layout, every level of detail's triangles one after another (`Levels`); `image.rs` reads PNG, JPEG, BMP, DDS (DXT1/3/5; the install's `.tex` files are DDS) and KTX2 (BC1/BC3, Zstandard-compressed levels; Roblox's material textures) through the `image` crate, recognized by their bytes, into RGBA8 with a full mip chain (alpha-weighted, at most 1024 pixels a side). A `Loader` request can ask for a mesh or an image (`Want::Mesh`, `Want::Image`): the worker decodes it into `Fetched::mesh` or `Fetched::image`, and bytes that don't decode fail as `Invalid` (or `UnknownVersion`, for a version Rook doesn't read yet). `rook-scene` logs each failure with the instances it hit ([data and logging](../data-and-logging.md#logging)). `Want::for_property` says what a content property must hold; PreloadAsync asks this way (a sound in a Decal's `Texture` fails, as in Studio), `rook content --place` totals the results, and the player asks for everything it draws. At startup `rook-scene` (`Installed`) loads the install's `head.mesh` and `textures/studs.dds`, from disk only, and the player hands them to `rook-render`, which otherwise draws its own.
