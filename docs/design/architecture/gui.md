# GUI

`rook-gui`. Part of the [architecture](../architecture.md).

Built from creator-docs and Studio observation only. Covers LayerCollectors (ScreenGui, SurfaceGui, BillboardGui), `UDim2` + `AnchorPoint` + `AutomaticSize`, the UI layouts, padding and constraints, `ZIndexBehavior`, `ClipsDescendants`, ScrollingFrame, `TextScaled`/`TextWrapped`/`RichText` (HarfRust shaping, Rook's own lines), `ImageRectOffset`/`ScaleType`/`SliceCenter`, input hit-testing and GUI events. The output is draw lists for the renderer.

Its `Gui` lives in `rook-lua`'s `World` beside the physics world, for the same reason: scripts read layout (`AbsoluteSize`), which lays out first when the journal shows GUI changed. The engine lays out once a frame after RenderStepped too, firing Changed for what moved. The draw list is `rook_types::GuiQuad`s, which `rook-scene` hands the renderer; the renderer draws them into an 8-bit layer that the tone pass lays over the frame in sRGB. Images don't change layout, so the drawing side loads them: `Gui` asks for the images it draws (`take_image_requests`), `rook-scene` loads them with the scene's other files and hands back their sizes (`image_arrived`), and the renderer uploads them like any image, quads naming each by its hash.

## Redrawing what changed

GUI is drawn in retained mode, as established UI engines draw it: Unreal's Slate caches each widget's draw elements and repaints only widgets invalidated for paint or layout, Godot keeps each CanvasItem's command list until it's marked for update, Unity's uGUI rebuilds only dirty Graphics' meshes, and browsers repaint only invalidated elements. All of them keep per-element draw data and batch from it; they differ in how they batch (Unity rebuilds a canvas's whole batch on any change, Slate and Godot re-batch cheaply from the cached elements). Rook follows Slate and Godot.

- **Pieces.** The screen is an ordered list of pieces: one per stacked object, holding the quads it draws of itself (background, style, bars, image, text, caret, stroke), already moved below the top bar. A CanvasGroup is one piece holding its group; the Hints and Messages are one more, found from the journal as they're parented (as world GUIs are), not by searching the Workspace. Each piece is an `Arc`, so whoever holds the last list can tell which pieces are new by pointer. A world GUI's canvas is still drawn whole when anything on it changes; giving canvases pieces the same way is the next step here.
- **Invalidation.** Changes arrive as they do for layout (`Gui::note_changes`): a look change (`restyled`) repaints the changed object's piece; an object placed again on its own (`shifted`) has its subtree's stack entries (place and clip) recomputed and the changed ones repainted, and one under a hidden object does nothing; a tree laid out again is restacked, keeping every piece whose stack entry didn't change and repainting the objects the change named (a label's text, an image arriving); trees coming or going, the screen resizing or a font arriving redraw everything. A change to an object inside a CanvasGroup repaints the group's piece. In a `Sibling` stack each object is followed by the run of all it holds (each entry keeps its depth), so an object hidden, shown, added or taken out restacks only the run of the nearest object still shown, as browsers rebuild only the dirty part of a stacking context; a `Global` stack spreads what an object holds through it, so there the ScreenGui restacks whole. Hit-testing reads these same stacks rather than stacking every ScreenGui again per mouse move, so what takes the mouse is what shows.
- **Text.** Shaping is the costly part of laying text out and doesn't depend on the size, so `Fonts` keeps runs shaped before by face and text (two generations, the older dropped once the newer fills), as browsers keep a word cache: a list's rows showing text they showed before aren't shaped again. Plain text whose color, transparency or outline alone changed keeps its laid-out glyphs and takes the new colors in place.
- **Renderer.** `GuiPass` keeps each piece's packed quads (glyphs placed in the atlas, gradients in the ramps) and its draw runs. New pieces are packed; kept ones aren't touched. When every piece keeps its quad count, only the changed pieces' ranges are written to the quad buffer; otherwise the buffer is written again from the packed pieces, without packing anything. Runs are joined across pieces. If the atlas or the ramps fill and start over, everything is packed again, as before.
- **World canvases follow their parts.** A SurfaceGui's or BillboardGui's place is worked out when its canvas is given to the renderer, which keeps it; after that a frame places again only the canvases on what the frame's render changes say may be somewhere new (`RenderChanges::maybe_moved`: parts moved, changed or gone, Attachments changed or moved in the tree), found through an index from each adornee, and an Attachment's part, to the canvases on it (`Gui::world_places_moved`), as a scene graph updates only dirty transforms. Tags over heads move with their Humanoids every frame. On a place with 897 world canvases, 27 of them on moving parts, placing them went from 0.52 to 0.05 ms a frame.
- **Cost.** With nothing changed, a frame does nothing for GUI. One object repainted each frame (a spinner, a ticking label) costs its own quads' emission and packing, a write of its range, and a walk over the piece list to join runs: proportional to the pieces (thousands at most), never to the quads or glyphs of the whole screen. Measured on a 296k-part place whose 3,765-object ScreenGui has a spinner: drawing the screen fell from 1.35 to 0.011 ms a frame and its upload from 0.19 to 0.019 ms.
