# Rendering

`rook-render`, and the scene `rook-scene` builds for it. Part of the [architecture](../architecture.md).

- Render proxies per visual instance (parts, MeshParts, SpecialMeshes, Decals/Textures, lights, particles, beams), built from snapshot deltas.
- Primitive meshes generated in code. Mesh and texture caches are fed by `rook-content`.
- Built-in mesh shapes (SpecialMesh `MeshType`, BlockMesh, CylinderMesh) reuse the part shapes: `rook-types` decides what a part's mesh draws and at what size (`MeshKind::look_on`, which also says which parts ignore mesh children), and the snapshot turns that into a draw shape (`DrawShape`: a part shape, the head or a mesh file), a size and, for the upright CylinderMesh, a turned rotation. The only new geometry is Rook's own head mesh. Meshes change only how a part looks; physics keeps the part's shape.
- File meshes (FileMesh, SpecialMesh FileMesh, MeshPart): `rook-types` gives their scale (`MeshLook::File`, `mesh_part_scale`), and the mesh's own origin sits at the part. The scene builder (`rook-scene/src/content/loader.rs`) asks a `rook-content` `Loader` for a file the first time a part needs it (`Want::Mesh`, so the worker threads also decode it), polls finished files once per frame and redraws only the parts waiting for them, nearest the camera first, within the frame's budget for arrivals ([per-frame budgets](threads-and-frames.md#per-frame-budgets)). A frame never waits; a screenshot does. While a file loads, or after it fails, a part keeps what its mesh drew before (the old mesh, or the empty-`MeshId` box) and a new mesh draws nothing, as observed in Studio. The scene carries each mesh by the BLAKE3 hash of its bytes (`MeshHash`); the renderer uploads each file once and draws every part using it in one instanced batch, like the primitive shapes. No loader starts for a place without file meshes.
- Terrain: the DOM holds each Terrain's voxels decoded (`rook-dom`'s `voxels.rs`; `SmoothGrid` is their saved form), and an edit journals only its region (`Change::Voxels`), which physics, replication and the renderer each take as the chunks holding it, sharing their voxels (copy on write). `rook-terrain` decodes `Terrain.SmoothGrid` and meshes it as Roblox does (surface nets, then each material's vertex moves, from Studio's terrain material table). The scene builder (`rook-scene/src/terrain.rs`) meshes it a chunk per worker (`rook-platform`'s `workers`) when the place loads, and hands each chunk's surface per material and facing (top, side, bottom) to the renderer as a mesh file marked as terrain (`rook_content::decode::mesh::TerrainMapping`), with the material's texture pack as its maps (`ContentRef::TexturePack`). The renderer's only terrain code is in the parts shader: terrain vertices take their textures from the world plane they face most, through the color map's tint mask; and its voxels go to the light voxels too (`rook_render::TerrainVoxels`, the chunks an edit changed), where how full each is dims the sun and the sky's light.
- **Trusses**: `rook-types` (`truss.rs`) holds the rules: how Size snaps (`truss_size`, used by `rook-lua`'s Size setter), the drawn shape (`TrussShape`: a Style and a segment count, a one-segment truss counting as NoSupports so it shares one mesh) and how it sits on the part (`TrussLook`: the turn onto the long axis and the offset to the box's low end). The snapshot gives the part `DrawShape::Truss` with that turn and offset in its `Pose`, so moving it only moves its instance; `rook-render` builds a shape's bars (`mesh::truss`) the first time a truss of that shape is drawn and draws every such truss in one instanced batch, so a truss costs one instance, whatever its length. Physics keeps the box. Files save `Style` as `style`, a separate property in the database; scripts' `Style` is a view of it (`SAME_AS` in `rook-lua`).
- **Images** (mesh `TextureId`, MeshPart `TextureID`, Decals, Textures) load the same way as mesh files, through the same `Files` and `Loader` (`Want::Image`: the workers decode to RGBA8 and build the mips). The scene carries each image by the BLAKE3 hash of its bytes (`ImageHash`, in `Scene::images`). A mesh texture is a property of its part's scene entry (`PartInstance::texture`, multiplied by `VertexColor`); each Decal and Texture is a scene entry of its own (`Layer::Image`), at its part's transform, kept in its part's list of layer indices so that parts and their images update in place together. What goes where follows `rook-types`: the face frames, the dominant-axis rule for round shapes and the tiling (`NormalId`, `Tiling`), which meshes take textures and follow UVs (`MeshKind::takes_texture`, `decals_follow_uvs`, `shows_surfaces`) and materials (`MaterialLook`); the shader reads the face frames from a uniform filled from `NormalId`. While an image loads a Decal draws nothing and a mesh is black; after a failure the Decal draws nothing and the mesh keeps the part's color, as observed in Studio.
- **GPU cache** (`rook-render/src/gpu/cache.rs`): one scheme for mesh files and images, `GpuCache` keyed by content hash. The first entry that needs a file queues it; uploads go up at the start of a frame within a budget of 2 ms and 24 MB ([per-frame budgets](threads-and-frames.md#per-frame-budgets)), so hundreds of images arriving at once spread over frames, and entries waiting for an upload draw nothing until it is done (a screenshot uploads everything first). Images are kept on the GPU for the renderer's life, and their pixels in memory only until they go up: the scene hands each image over as it loads (`Renderer::take_images`), keeping only its size and average color, and the renderer holds it parked until something draws it; a mesh file's room in the pool is given back when the player drops it (grass tiles). Opaque parts are batched by (shape, image), images on parts by (`ZIndex`, shape, image) in a second set of batches, both with the in-place slots of `update_parts`; missing images stand in as a 1 × 1 white image (a flat normal for normal maps).
- **Draws** (`rook-render/src/gpu/pool.rs`, `batch.rs`, `renderer/draws/runs.rs`): every mesh's vertices and indices live in a few shared buffers (`MeshPool`), in pages that grow up to the device's biggest buffer (1 GiB at most), so one page holds a whole place (an 86k-part place's terrain alone is 6.6M vertices). Positions are their own vertex stream, so the shadow pass reads 12 bytes a vertex; normals, UVs, box points and faces are a second. Each set of batches keeps its instances in one buffer, each batch a run of slots that moves when it fills; changed instances go up packed with their slots and a compute pass copies each into place (`batch/scatter.rs`, as Unreal's GPU scene does), recorded in the frame's one command buffer ahead of its passes, as the other uploads' copies are; a pool bigger than a storage binding goes up in 64-instance chunks instead. Every image sits in one table of two binding arrays (sRGB and linear views, the same slots), and each instance names its five images' slots, so draws with different images bind nothing between them. A frame lists each pass's visible batches in drawing order as indirect draw arguments and joins consecutive ones sharing pipeline, instance buffer and pool page into a run, one `multi_draw_indexed_indirect` each: on an 86k-part place 1 + 6 draw calls for 321 + 620 batches. The draw order is the batches' own, so frames are byte-identical to drawing each batch alone. Adapters without binding arrays get a bind group per image set, bound per run, and adapters without first instances in indirect draws (`INDIRECT_FIRST_INSTANCE`) issue each draw directly; the frames are the same (test `table_and_multi_draws_draw_what_bound_sets_draw`). A batch's culling box grows with each changed instance and is worked out tight again once as many instances changed as it has.
- **World GUI draws** (`rook-render/src/renderer/gui/world.rs`, `renderer/passes/cuts.rs`): every SurfaceGui's and BillboardGui's quads share one buffer, each quad beside its canvas's id in a second vertex stream, and stay there until that canvas changes (ranges handed out by the mesh pool's `RangeAlloc`). Each frame skips the canvases wholly out of the camera's view (a box around their quads, which can reach past the canvas), writes where every other canvas is into one storage array the shaders read by id, and lists their runs as indirect draws in drawing order; the runs in a row with one image and pipeline are one `multi_draw_indirect`, as the parts' runs are. Canvases sort among the transparent parts, and each place one is drawn between them breaks the parts' runs, so a canvas goes not where its distance alone sorts it but anywhere between the farther and nearer transparent instances its box on the screen overlaps, where blending order shows (found through a 16 by 16 grid of screen tiles listing the instances that reach each, in drawing order), and canvases that can share a place are drawn there together, the canvases kept in their own order: the frame is the same pixel for pixel. On a place with 897 canvases, turning: 82 cuts a frame to 23, main pass calls 185 to 89, its encoding 1.25-1.30 to 0.81-0.86 ms (1.6-2.5 ms before the canvases shared a buffer); standing still, 76 calls to 28 and 0.91-0.96 to 0.67-0.69 ms. Adapters without first instances in indirect draws issue each draw directly (tests `world_canvases_in_a_row_draw_in_one_call`, `world_canvases_sort_among_the_transparent_parts_they_overlap`).
- **Levels of detail** (`rook-render/src/renderer/draws/detail.rs`): a mesh file's levels share its vertices and sit one after another in the pool, so a level is only a different index range in the draw's arguments. While a pass builds its draws, each run of a batch it sees is split where its instances' levels change (`push_draws`), so the cost follows the instances drawn and meshes of one level skip it. `Detail` owns the choice: Studio's distance rule ([file meshes](../../behavior/meshes/file-meshes.md#levels-of-detail)), plus the hysteresis engines use (Unreal and Unity cross-fade instead; Rook draws no blend, so it holds a coarser level until the camera is 5% nearer than the threshold, where Studio flips back at once). Each scene entry keeps its level, and image layers, adornments and Highlights take their part's (`PartInstance::drawn_over`), so a decal never shows a different mesh from the one it's on. The shadow pass draws the camera's levels, as Unreal and Unity do.
- **Image layers** draw after the opaque parts and before the transparent ones, blended, testing depth with `GreaterEqual` and writing none: they reuse the part's own mesh and vertex maths (the clip position is `@invariant`), so they lie exactly on it. A layer projected onto a face keeps only the points whose part-space normal is closest to its face's axis and lie inside the face's box; a mesh-UV layer covers the whole mesh. Layers of a partly transparent part are sorted with the transparent parts, just after their own. Layers never enter the shadow pass.
- **Materials and surfaces:** `MaterialLook` decides: Plastic draws its faces' surface patterns (studs, the weld/glue lattice, inlets, universal), Neon is drawn unlit, the rest plain, Reflectance mixes towards the sky color (Approximation). The patterns are a four-layer texture array: from the user's install (`textures/studs.dds`, handed over by the player at startup like `head.mesh`) or Rook's own drawn patterns. The 2022 materials' textures aren't in the install (Studio downloads them), so Rook draws those materials plain; nothing from the install is ever committed.
- **Particles** (`rook-render/src/effects/particles.rs`, drawn by `renderer/effects/particles.rs`) cost what's in view, as Studio's do ([particle emitters](../../behavior/effects/particle-emitters.md)). `set_time` only adds to the time owed; the frame's draw moves particles on (`Particles::frame`): each emitter whose particles' box, or the box it births in, meets the view frustum steps once by the frame's time (at most 1/15 s, Studio's step; one worker task per emitter once there are more than 2,048 particles to step, since waking the workers costs about that much), and every other emitter is left untouched, its time stopped until the camera turns back, which is what Studio does. An emitter's `Rate` thins with its distance from the camera. Of the emitters in view, Studio's budget (`within_budget`) draws whole emitters nearest first up to 16,000 particles; only those are built into instances and sorted. Emitting is bookkeeping: `Emit` and births push a record, and a locked emitter's particles are kept along its axes, so moving it costs nothing until it's drawn. A frame's cost is the in-view emitters' particles (`particles: stepped` in the bench counters) plus at most 16,000 drawn; emitters out of view cost one box test each.
- Lighting: Lighting service properties (ClockTime → sun, Ambient/OutdoorAmbient, Brightness, Atmosphere, Sky, post effects). A forward renderer; Future (clustered) lighting comes later. The sun's direction follows `Lighting:GetSunDirection()` as measured in Studio (`sun_direction` in `rook-types`' clock, which the method returns too; see [the clock](../../behavior/lighting/clock.md)).
- Sun shadows (`rook-render/src/lighting/shadow.rs`): before the main pass, a depth-only pass draws the opaque batches' existing instances from the sun into one 2048² `Depth32Float` map, reverse Z like the main pass (compare Greater, clear to 0). It reads only the mesh pool's positions and uses the main shader's own vertex maths (`placed`, shared by `vs_main` and the `vs_shadow` entry point) and a pipeline layout without the shadow map's bind group, which the pass is writing. The orthographic box holds the smallest sphere around the camera's view out to 300 studs, so its size changes only with the field of view and aspect, and its center moves in whole texels across the sun's view, so a texel's footprint stays put as the camera moves; it reaches 500 studs further towards the sun for tall casters off screen. Against acne the casters get a slope-scaled depth bias and receivers look up the map 1.5 texels out along their normal plus 0.05 studs towards the sun. The main pass multiplies only the sun term by 3×3 linear-filtered comparison samples, fading to lit over the last fifth of the distance. Each instance carries a cast flag (`BasePart.CastShadow`) that the shadow vertex shader uses to clip non-casters, so batches and their slots are unchanged; transparent parts live outside the opaque batches and never cast. The snapshot sets `Lighting::global_shadows`; with it off, or the sun below the horizon, no shadow pass is encoded. Without `PrioritizeLightingQuality` there is no shadow pass either: the sun shadows through the light voxels, each voxel's cone towards it (voxel cone tracing) reading a sun cover with mips per layer (`lighting/local/cover.rs`), rebuilt only over the tiles whose blockers changed.
- Every lighting and material formula is documented with its source and confidence.
