# Thumbnails

Checked against Studio 0.747 on 2026-11-15.

Images Roblox renders of an asset, an avatar, a badge or a group, which image properties name with `rbxthumb://` or with the old web URLs places from before it still hold (an inventory's item icons, a player list's headshots). How other content loads is in [asset fetching](asset-fetching.md).

Code: `rook-content`'s `reference/thumbnail.rs` turns every form into one thumbnail request, and `resolver/thumbnails.rs` asks the thumbnails service for it; the resolver fetches the image from the CDN and caches it like an asset (`resolver/download.rs`). `Players:GetUserThumbnailAsync` is in `rook-lua`'s `api/methods/web/users.rs`.

## How it was measured

In Studio, each form was set as an ImageLabel's `Image` and passed to `ContentProvider:PreloadAsync`: `Success` means it loaded. `AssetService:CreateEditableImageAsync` reads an `rbxthumb://` image back, which gives its size in pixels (it refuses the old URLs). For the old URLs, the size came from `ImageRectSize`, which is in image pixels: a label shows the whole image when the rectangle is at least as large as the image, and part of it otherwise. Rows of labels with rectangles of each candidate size, on a SurfaceGui, were compared in captures. Failures were drawn on white and on the part's color. Studio's log names any web request that failed, and none did for a refused size, so Studio refuses those without asking the service.

## `rbxthumb://`

`rbxthumb://type=<type>&id=<id>&w=<width>&h=<height>`, with `&filters=circular` for an image cut to a circle.

- Keys in any case (`Type=`, `ID=`, `W=`) and in any order; other keys (`format=`, `x=`) are ignored. When a key is repeated the first wins (`id=<good>&id=1` loads, `id=1&id=<good>` doesn't), unlike asset URLs, where the last `id` wins.
- The type is matched exactly: `type=asset`, `type=ASSET` and `type= Asset` load nothing.
- Ids and sizes read like asset ids: spaces around them, a `+` and leading zeros are fine; `5abc`, `-5` and `0` aren't. Trailing spaces after the URL are fine; a leading space or an upper-case scheme loads nothing.
- `w` and `h` must both be given and be one of the type's sizes below, which Studio checks itself: the service would serve an Asset at 30x30 or a headshot at 50x50, and Studio refuses both.
- `filters=circular` cuts the image to a circle (a headshot lost about a sixth of its opaque pixels); any other filter value is ignored.

| Type | Sizes that load |
|---|---|
| `Asset` | 150x150, 420x420, 700x700, 256x144, 384x216, 480x270, 768x432 (not 576x324) |
| `AutoGeneratedAsset`, `BundleThumbnail`, `DeveloperProduct`, `GroupIcon`, `Outfit` | 150x150, 420x420 |
| `Avatar` | 48, 60, 100, 150, 180, 352, 420, 720 (square) |
| `AvatarBust` | 48, 50, 60, 75, 100, 150, 180, 352, 420 |
| `AvatarHeadShot` | 48, 60, 100, 150, 180, 352, 420 |
| `BadgeIcon`, `GamePass` | 150x150 |
| `FontFamily` | 1200x80 |
| `GameIcon` | 50, 128, 150, 256, 512 |
| `GameThumbnail` | 256x144, 384x216, 480x270, 576x324, 768x432 |

Tried against every size the service serves for any type (30 to 1200 wide). `PlaceIcon`, `HeadShot` and `AvatarThumbnail` load nothing. The service answers an Asset's wide sizes with a square image of the height (256x144 is 144x144), and Studio draws that.

## The old web URLs

Studio turns these into thumbnail requests itself, whatever the host: `example.com` works as well as `www.roblox.com`, and Roblox's site answers 404 for all of them now. The scheme is `http` or `https` in any case, or `rbxhttp://` followed by the path. The path is matched without case, with doubled slashes fine and a trailing slash not.

| Path | Thumbnail | Id keys | Sizes it snaps to |
|---|---|---|---|
| `Game/Tools/ThumbnailAsset.ashx`, `thumbs/asset.ashx`, `asset-thumbnail/image` | Asset | `assetid`, else `aid` | 150, 420, 700 |
| `thumbs/avatar.ashx`, `avatar-thumbnail/image` | Avatar | `username`, else `userId` | 30, 48, 60, 75, 100, 110, 140, 150, 180, 250, 352, 420, 720 |
| `headshot-thumbnail/image` | AvatarHeadShot | `username`, else `userId` | 48, 50, 60, 75, 100, 110, 150, 180, 352, 420, 720 |
| `bust-thumbnail/image` | AvatarBust | `username`, else `userId` | 48, 50, 60, 75, 100, 150, 180, 352, 420 |
| `outfit-thumbnail/image` | Outfit | `userOutfitId` | 150, 420 (Inference: the service's outfit sizes; not measured) |

- The size is `width`, `wd` or `x` and `height`, `ht` or `y`, mixed as they come (`wd=420&y=420` loads). Both are needed; `w` and `h` don't count. A size is any whole number, signed (`wd=-5` and `wd=0` load), and is snapped to the nearest size the form takes, the smaller on a tie: an asset's 285 gives 150 and 286 gives 420, 560 gives 420 and 561 700, and anything from 20 to 130 gives 150; a headshot's 165 gives 150, 200 gives 180, 300 352 and 600 720; an avatar's 30, 75 and 110 stay as they are. The avatar sizes are exactly the ones the service's `v1/users/avatar*` endpoints take, so the old URLs reach sizes `rbxthumb://` refuses (a headshot at 720).
- When sides differ, the snap isn't the nearest square: 150 by 420 gave an image larger than 150 and smaller than 420, and 1000 by 1 a wide one. *Approximation:* Rook snaps the mean of the two sides.
- Ids read like asset ids, the first of a repeated key winning; `assetid` wins over `aid` wherever they are, and a `username` over a `userId` (a name that doesn't exist fails even with a good id beside it). `userId=0` and `id=` (not an id key here) load nothing. Names are looked up without case (`BUILDERMAN` loads).
- `fmt`, `format` and other keys are ignored.
- Other paths load nothing: `thumbs/headshot.ashx`, `Thumbs/GroupIcon.ashx`, `Thumbs/BCOverlay.ashx`, `badge-thumbnail/image`, `group-thumbnail/image`, `game-pass-thumbnail/image`, `place-thumbnail/image`, and any other `.ashx`.

## Meshes

A thumbnail in a `MeshId` fails to load (`PreloadAsync` gives `Failure`): it's an image. Rook fails it the same way, as bytes that don't decode as a mesh.

## Failures

A thumbnail that doesn't load draws nothing, like any image that fails ([asset fetching](asset-fetching.md)), on a transparent label and on a white one alike: a refused size, a type or path Studio doesn't know, and an id the service has nothing for (it answers `Error` with the URL of a broken-image picture, which Studio doesn't draw).

## The thumbnails service

Rook asks the `thumbnails` domain ([web endpoints](../../design/web-endpoints.md)) `POST /v1/batch` with `[{"requestId", "targetId", "type", "size": "<w>x<h>", "format": "png", "isCircular"}]`, the type by its `rbxthumb://` name; the batch request takes those names as they are. It answers `{"data": [{"state", "imageUrl", "errorCode", "errorMessage"}]}`:

- `Completed`: `imageUrl` is the image on Roblox's CDN.
- `Pending`: still being rendered. Rook asks again, waiting a quarter of a second and doubling to two seconds, for ten seconds in all, as Studio waits (its `DFIntThumbnailContentProviderTimeoutSecs` is 10), and then fails it for the run.
- `Error`: no such thumbnail (an asset that doesn't exist; error code 3 for a size the service doesn't serve). `Blocked`: refused.
- Anonymously, the service refuses `AutoGeneratedAsset` ("User not authorized") and doesn't serve `FontFamily` through the batch request, so those fail in Rook.

A username is looked up first on the `users` domain, `POST /v1/usernames/users`. Studio does the same on Roblox's own; Rook asks only when the `users` domain has an endpoint, which it hasn't by default (its scripting APIs answer locally), so by default a thumbnail by username fails as offline.

Studio's fetcher sends up to 100 thumbnails in one batch request (its `DFIntBatchThumbnailLimit`). Rook sends one per request: its loader resolves a few references at a time, so there's little to batch.

*Caching:* an image is kept in the cache under its request (`thumb-AvatarHeadShot-156-150x150`), so a second run needs no network. Avatars and icons change, and Studio asks every session, so Rook uses a stored thumbnail for a day, then asks the service again; when the service can't be reached it still draws the stored one. A thumbnail the service has nothing for is remembered for a day, as a missing asset is.

## `Players:GetUserThumbnailAsync`

`GetUserThumbnailAsync(userId, thumbnailType, thumbnailSize)` returns the `rbxthumb://` URL and whether the service has it ready:

- `HeadShot` gives `type=AvatarHeadShot`, `AvatarBust` `type=AvatarBust`, `AvatarThumbnail` `type=Avatar`; the size enum's item gives `w` and `h` (`Size48x48` is 48), every combination one `rbxthumb://` loads.
- The URL is built whatever the id: `id=-1` and `id=0` for those, a fractional id cut to a whole one, a string read as a number. Ready is `false` for an id of 0 or less and for a user who doesn't exist, `true` once the image is rendered.
- The type and size take an EnumItem, its number or its name; anything else raises `Unable to cast double to ThumbnailSize` (a number that's no item) or `Unable to cast Material to ThumbnailType` (another enum's item), and a missing one `Argument 2 missing or nil`.

Rook asks the same batch request for ready; with no `thumbnails` endpoint, nothing is ready. *Inference:* a request that fails is not ready rather than an error (not checked against a Studio that can't reach the service).
